Case study 2 — 2025 to 2026

A design system engineers actually use

The company asked for a design system. What it needed was a small, opinionated one that nineteen engineers could build with unsupervised, and a navigation that made the app feel like one product instead of a collection of features. This is how the system, the page pattern and the sidebar came together.

Role
Design system designer and lead. Tokens, components, page patterns, sidebar, and the front-end polish pass with engineering.

Where I started

The system, before any screen

I'm a design system designer. I spent three years building one at Carvana, and I took that work and put it straight into practice here. The system I built for LightSource is consistent and limited, but has every capability the product needs.

The biggest lesson I carried over, from Dave Williams, the manager who helped me build the Carvana system, is that a design system is only as good as the engineers who use it. A lot of systems get built in a vacuum by design teams who never think about the engineering experience. So this one is engineering-first: useful classes, semantic tokens, and all of it implemented inside Tailwind, which is what the engineers were already writing.

That choice did more than any component. A robust, limited system equips engineers to do front-end work well without a designer looking over their shoulder, whether they're writing from scratch or with tooling. Across the board, it led to better outcomes than reviewing every screen ever could.

And the palette came pre-decided. The rebrand had already fixed one orange, a near-black and a neutral scale, and the product interpretation was settled: airy, white, with orange held back for the few moments that carry the brand. The system's job was to make those decisions the path of least resistance.

Limited, but complete

A small set of tokens and components that covers every case, rather than a large set that covers each case slightly differently. If a new need appears, the first question is which existing pattern it belongs to.

Engineering-first

Semantic tokens and useful classes in the Tailwind the team already used. The system lives where the code lives, so using it is easier than not using it.

Brand-constrained

White ground, neutral hierarchy, one orange used rarely. Every screen reinforces the brand, and the restraint is what makes the orange mean something when it appears.

Unifying the visual language

Every page opens the same way

The strips below are the classic page headers, cropped from the live app, beside their Nova equivalents. In classic, the primary action is an orange gradient on Items, blue on the sourcing project, blue in a different size on bid comparison, blue again on Programs, and a black button sitting right beside an orange one on the item list. Some pages open with a title and subtitle, some with a search bar, some with a banner. Secondary actions like Export are styled as loudly as primary ones.

Nova replaces all of it with one page-header pattern. The page name sits top-left. A toolbar on the right carries search, filter, column options and expand in one weight, and the single primary action is always the last element, always the same filled dark button. Underneath, one table component with the same row height, chips, status pills, number alignment and hover states on Items, BOMs, RFIs, Contracts, Programs and Sourcing projects. Hierarchy comes from weight and spacing rather than color, so the eye lands on the record, then the status, then the action.

Because the header and table are one component, adding a page means configuring them, not designing them. That's what a learning curve looks like from the inside: learn one page, and you've learned them all.

The sidebar

Two navs became one

Classic had a top nav and a left nav. The top bar carried global search, a link to the supplier side of LightSource, the Help Center, the agent, notifications and the avatar. The sidebar carried the destinations, a gradient "New Sourcing Project" pill, and the team and account buried in a chevron at the bottom, with display preferences hidden inside that menu. I consolidated all of it into a single left nav.

The idea was to make the sidebar feel like the user's workspace. So the team name moved to the top, with a team selector that replaced a very janky one, partly to make switching intuitive and partly to encourage teams to grow inside LightSource. The nav items were grouped by category, and I went very deep on the icon design and alignment; there are a lot of turns on that in the Figma. The username moved to the bottom, and all settings moved down next to it.

The hardest single problem was display preferences. Currency, rounding and language are core features people use constantly to see things in their own terms, and they had been buried in a menu. Finding a place for them that made sense to an end user took real iteration; they ended up as visible rows in the footer.

The other challenge was collapse. The old sidebar expanded and collapsed on its own through a Tailwind behavior. I wanted it deliberately openable and closable, with a real collapse control, and I wanted the collapsed state to stay functional rather than decorative. Everything in the sidebar got touched.

Nova shipped as an opt-in toggle. We have too many users to flip everyone at once, and I didn't want to disturb anyone's flow. Running it as a beta also meant early feedback from real customers on what worked and what didn't, so we could be sure we were accelerating the workflow rather than just redesigning it. Classic stays the default until the last features reach parity.
